## Executive Summary

- **小程序定位为“门店现场经营助手”。** 它只承担当场必须完成的查询、新增和提醒，不承担批量治理、复杂分析和高风险管理。
- **五个底部入口继续保留。** 首页看状态，商品查库存，记一笔处理拿货/卖货/快速收支，账本看经营摘要，我的管理当前身份与同步。
- **复杂能力迁出但业务不断链。** 手机仍可快速建档、单笔拿货、单笔卖货和单规格库存核对；完整商品维护、删除/停用、批量盘点、全量报表、权限和导入导出由管理后台承接。
- **权限和数据一致性由服务端负责。** 不同角色看到不同字段和动作；手机与后台写入同一店铺数据源，禁止再使用整店数据最后写入覆盖。

## 1. 产品定位与目标

### 1.1 一句话定位

帮助服装与化妆品门店员工在手机上快速查货、记拿货、记卖货，并让店主随时掌握今天的库存和经营情况。

### 1.2 核心目标

1. 常用商品可在 10 秒内找到对应规格库存。
2. 已有商品的卖货登记可在 30 秒内完成。
3. 已有商品的单笔拿货登记可在 45 秒内完成。
4. 店主打开首页后 5 秒内看懂今日销售、今日盈利和待处理事项。
5. 店员无法通过隐藏入口或直接接口调用越权查看成本、盈利或执行高风险修改。

### 1.3 非目标

- 不在手机上做批量商品导入、批量编辑和完整规格矩阵维护。
- 不在手机上做月底批量盘点、库存审批和全量审计。
- 不在手机上承载 7/30 天、12 个月等完整经营分析。
- 不在手机上配置员工角色、基础资料和全店规则。
- 不建设顾客商城、在线支付、会员积分和专业财务会计。

## 2. 用户与权限

| 角色 | 默认可用能力 | 默认不可用能力 |
| --- | --- | --- |
| 店主 | 全店查询、拿货、卖货、快速收支、受限商品编辑、库存核对、成本与经营摘要 | 批量维护和完整审计需进入后台 |
| 管理员 | 商品查询、拿货、卖货、库存核对；是否看成本由店主授权 | 员工权限、数据导出等敏感能力按授权开放 |
| 店员 | 商品与库存查询、拿货、卖货、本人近期记录 | 成本、盈利、商品停用、库存直接覆盖、员工管理 |
| 财务 | 销售与收支查询、经营摘要、快速收支（可配置） | 商品和库存管理 |

若用户没有某项权限，页面不展示入口；即使绕过页面调用接口，服务端也必须拒绝。

## 3. 信息架构

| 底部入口 | 核心任务 | 主要页面 |
| --- | --- | --- |
| 首页 | 看状态、处理异常、进入高频动作 | 今日概览、待关注、最近变动 |
| 商品 | 查商品、查规格库存、快速建档 | 商品列表、商品详情、快速建档 |
| 记一笔 | 快速记录经营动作 | 拿货、增加库存、卖货、其他收支、库存核对 |
| 账本 | 看经营摘要和近期流水 | 今日/昨日/本月摘要、近期记录 |
| 我的 | 确认身份与同步状态 | 当前店铺、角色、同步状态、关于、退出 |

## 4. 页面与功能需求

### 4.1 登录与选店

#### 页面内容

- 微信头像与店主/员工姓名。
- 微信身份和云端数据说明。
- “微信账号登录”主按钮。
- 登录后若只属于一家店，直接进入首页。
- 登录后若属于多家店，展示可进入的店铺列表和本人角色。
- 网络异常且本机有有效会话时，可进入只读或受限离线模式。

#### 规则

- OpenID 只用于识别用户，不再直接代表店铺。
- 登录结果必须包含 `userId`、可访问的 `storeId`、角色和权限集合。
- 被停用成员不得继续读取或写入店铺数据。

### 4.2 首页

#### 首屏信息

- 店铺名称、日期、当前同步状态。
- 当前库存总件数；有成本权限时展示库存成本。
- 今日销售额、今日盈利、今日售出件数。
- 服装与化妆品库存概览。
- 缺货、低库存、临期和待审核差异数量。

#### 快捷动作

- 拿货/增加库存。
- 卖货。
- 库存核对。

#### 内容区

- 待关注事项按严重程度排序：临期、缺货、低库存、同步失败。
- 最近三至五条有效变动。
- 点击商品类提醒进入商品详情；点击记录进入对应近期记录。

#### 权限差异

- 无成本权限的店员不展示库存成本与盈利。
- 无库存修正权限的用户点击“库存核对”后只能提交差异，不能直接生效。

### 4.3 商品列表

#### 查询

- 支持名称、系统编号、货号搜索。
- 支持服装/化妆品切换。
- 支持分类与库存状态筛选。
- 默认按最近使用排序，可切换编号或库存状态。

#### 商品卡片

- 图片、名称、编号、货号。
- 规格数量、总库存、缺货/低库存状态。
- 有售价权限时显示参考售价。
- 不在列表展示完整成本和供应商信息。

#### 快速建档

手机端快速建档只要求：

1. 商品名称。
2. 服装/化妆品业务类型。
3. 分类。
4. 可选图片。
5. 一个默认规格；服装默认为“通用 / 均码”，化妆品默认为“通用 / 标准规格”。

保存后提示“商品已创建，可在管理后台完善规格与资料”。店主可继续添加少量规格，但一次最多 10 个组合；更复杂的规格矩阵在后台完成。

### 4.4 商品详情

#### 展示内容

- 图片、名称、编号、货号、分类。
- 规格库存列表。
- 参考售价；成本、供应商、批次等字段按权限显示。
- 最近拿货、卖货和库存变化。

#### 操作

- 卖货。
- 服装登记拿货；化妆品增加库存。
- 单规格库存核对。
- 店主可修改名称、图片、货号和参考售价等有限字段。

#### 不提供的操作

- 不提供直接删除商品。
- 不提供批量删除规格。
- 不提供重新排列商品编号。
- 商品停用和复杂规格维护统一在后台完成。

### 4.5 记一笔

#### 入口

- 服装拿货。
- 化妆品增加库存。
- 卖出服装。
- 卖出化妆品。
- 其他收入/支出（按权限）。
- 库存核对。

#### 交互原则

- 先选业务类型，再选商品与规格。
- 默认记住最近使用的收款方式，但提交前必须可见。
- 主要数字输入使用数字键盘。
- 提交前显示本次操作对库存和金额的影响。
- 提交成功后展示结果和“再记一笔”入口，避免重复提交。

### 4.6 单笔拿货/增加库存

#### 必填字段

- 商品与规格。
- 数量，必须为正整数。
- 服装拿货的单件进价。

#### 可选字段

- 供应商。
- 拿货单号或备注。
- 化妆品批次号、到期日期。

#### 结果

- 增加规格库存。
- 生成采购/库存流水。
- 更新移动平均成本或采用后台配置的成本规则。
- 记录操作者、终端和服务端时间。

### 4.7 单笔卖货

#### 必填字段

- 商品与规格。
- 数量，必须为正整数且不超过可售库存。
- 单价。
- 收款方式。

#### 可选字段

- 备注。
- 顾客称呼或内部单号（若后续业务需要）。

#### 结果

- 原子地写入销售记录、扣减库存并保存售出时单位成本。
- 提交成功页显示收款金额与剩余库存。
- 销售错误不得直接编辑历史记录；手机端提交纠错申请，后台执行作废、退款或冲正。

### 4.8 库存核对

- 仅处理一个商品规格。
- 展示系统库存，用户填写实际库存与原因。
- 店主或有权限管理员可直接确认生效。
- 店员只能提交差异，状态为“待确认”。
- 每次差异必须生成不可删除的审计记录。

### 4.9 账本

#### 默认展示

- 业务类型切换：服装、化妆品。
- 时间切换：今日、昨日、本月。
- 销售收入、已售商品成本、经营盈利、毛利率、销售笔数与售出数量。
- 最近销售、拿货和其他收支。

#### 数据权限

- 无盈利权限的店员只展示本人近期业务记录，不展示成本和盈利。
- 完整趋势、商品排行、收款构成、自定义日期和导出进入管理后台。

### 4.10 我的

- 头像、姓名、当前店铺和角色。
- 云端同步状态与最后成功时间。
- 权限说明。
- 管理后台使用说明，仅向店主/管理员展示。
- 版本说明、隐私说明和退出登录。
- 不再提供员工管理、供应商管理、分类设置和复制 CSV 等占位入口。

## 5. 核心业务流程

### 5.1 卖货

```text
首页/记一笔 → 选择卖货 → 选择业务类型 → 搜索商品
→ 选择规格 → 输入数量和单价 → 选择收款方式
→ 确认金额与剩余库存 → 提交 → 成功
```

### 5.2 拿货

```text
首页/记一笔 → 选择拿货/增加库存 → 选择商品规格
→ 输入数量与进价 → 选填供应商/批次 → 确认库存变化
→ 提交 → 成功
```

### 5.3 现场发现库存不符

```text
商品详情 → 库存核对 → 查看系统库存 → 填写实际库存与原因
→ 有权限：确认生效
→ 无权限：提交后台审核
```

### 5.4 新货尚未建档

```text
商品 → 新建 → 名称、业务类型、分类、图片
→ 使用默认规格创建 → 继续登记拿货
→ 后台稍后完善完整档案
```

## 6. 状态与异常处理

| 场景 | 处理方式 |
| --- | --- |
| 库存不足 | 阻止卖货并展示当前可售数量 |
| 数据版本冲突 | 不静默覆盖，提示刷新后重试 |
| 网络中断 | 未提交成功的写操作保持草稿；禁止假装成功 |
| 重复点击提交 | 按业务请求 ID 幂等处理，只生成一条记录 |
| 商品已停用 | 禁止新增卖货/拿货，历史记录仍可查看 |
| 成员被停用 | 清除写权限并要求重新登录 |
| 成本缺失 | 收入可统计，盈利标记为待补成本，不虚构为零成本 |
| 图片上传失败 | 允许先保存其他字段，图片保持待重试状态 |

## 7. 交互与视觉要求

- 延续现有浅蓝、淡粉、雾感玻璃视觉，但减少纯装饰性卡片。
- 一页只突出一个主要提交动作。
- 底部导航与主要按钮满足单手操作，触控区域不小于 44px 等效尺寸。
- 关键金额、数量和库存变化使用文字与正负号共同表达，不只依赖颜色。
- 表单错误就近展示，不能只使用短暂 Toast。
- 删除、冲正和权限配置等高风险操作不放在手机高频路径。

## 8. 数据与接口要求

- 所有业务请求必须携带 `storeId`，服务端从会话校验成员关系。
- 商品、规格、采购、销售、库存流水和收支记录分别存储，不再上传完整店铺状态。
- 拿货、卖货和库存确认使用事务。
- 图片上传云存储，数据中只保存可跨端访问的文件标识。
- 本地缓存只用于加速和草稿保护，不能成为权威数据源。
- 所有写操作返回服务端记录 ID、最新库存和最新版本号。

## 9. 验收标准

### 9.1 功能

- 五个底部入口职责清楚，不出现后台管理型占位菜单。
- 店员能独立完成查货、卖货和拿货，但看不到未授权成本与盈利。
- 快速建档后可立即登记拿货，复杂资料可在后台继续完善。
- 手机端不存在直接商品删除、历史财务删除和批量库存覆盖入口。

### 9.2 一致性与安全

- 手机与后台同时操作不同记录不会互相覆盖。
- 重复提交不会重复扣库存或生成重复流水。
- 库存不足、成员停用和越权调用均由服务端拒绝。
- 每个库存变化均能追溯到业务单据或库存修正记录。

### 9.3 体验

- 375px 宽度下无横向溢出，主要动作无需缩放。
- 核心页面具备加载、空数据、错误、无权限和离线状态。
- 主要流程可由键盘与读屏基础操作完成，表单具备可识别标签。

## 10. 后续问题与假设

1. 默认假设门店仍以单店为主，但数据与登录结构预留多店。
2. 店员默认不看成本和盈利，店主可在后台单独授权。
3. 手机端保留快速收支，但可通过角色权限关闭。
4. 完整商品编辑是否对店主保留，是上线前需要真机测试确认的体验决策。
5. 本文定义的是目标产品，不代表当前云函数和页面已经支持全部能力。
