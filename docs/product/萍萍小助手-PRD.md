## 2. 产品定位

萍萍小助手是面向小型零售门店的轻量经营管理系统，以服装经营为主要设计背景，当前同时兼容美妆商品。它帮助店主和店员完成商品建档、规格库存、卖货、拿货、账本、经营分析和操作追溯。

产品采用“小程序高频操作、Web 低频管理”的分工，不建设顾客商城，不处理在线支付、配送、专业财务会计、多门店调拨或完整采购审批。

## 3. 用户与权限

| 角色 | 主要能力 |
| --- | --- |
| owner | 全部经营数据、商品维护、安全删除、员工与权限 |
| admin | 按权限管理商品、库存、经营数据和员工 |
| finance | 按权限查看成本、盈利、收支和报表 |
| clerk | 商品与库存查询、卖货、拿货等日常经营操作 |

小程序和 Web 使用不同登录会话。权限由服务端判断；客户端只负责按权限隐藏入口。

### 面试 Demo

- Demo 用户固定为 `clerk`，令牌带 `demo=true`。
- Demo 登录固定绑定独立 Demo 店，不接受客户端传入的门店或角色。
- Demo 可以查看商品、库存和经营数据，可以卖货、拿货。
- Demo 不能编辑商品资料、永久删除、管理员工、修改基础设置、导出或访问真实门店。
- Demo 不允许使用本机其他门店缓存进行离线降级。

## 6. 商品与真实货号

### 标识职责

- `itemNumber` / `item_number`：用户真实货号，可空，最多 80 字符。用户可手动填写，AI 可从图片中识别辅助。
- `code`：系统生成的内部兼容流水号，创建后稳定，不面向普通用户展示，不作为真实货号。
- `productId`、`adminProductId`、`specId`：系统内部关联 ID。

商品名称和真实货号可用于普通搜索。真实货号为空时界面显示“货号未填写”，不得回退显示内部 `code`。

### 商品字段

通用字段包括名称、分类、真实货号、图片、成本价、参考售价、低库存阈值、货位和状态。服装使用颜色/尺码规格；美妆还可记录品牌、批次、到期日期、款式/色号和容量/规格。

新建商品可为每个规格填写非负整数初始库存；快速创建未填写库存时为 0。一次最多生成 40 个规格。

## 7. 库存

- 小程序按商品规格管理库存；Web 展示后台聚合库存。
- 库存状态：大于阈值为正常，大于 0 且不高于阈值为偏低，等于 0 为缺货。
- 卖货、拿货、AI 批量入库和后台库存操作均由服务端校验并记录审计。
- 同步过程中出现历史汇总规格时，客户端只展示真实有效规格，避免重复“全部规格”或将 104 件库存误判为异常。
- 小程序规格库存与 Web 聚合库存粒度不同，跨端一致性由 Node/Go 与 MySQL 兼容路径维护，前端不自行补值。

## 8. 卖货

用户选择商品和规格，填写正整数数量与售价。系统必须确认商品处于可经营状态、规格存在且库存充足，然后在同一服务端事务中扣减规格库存、更新后台聚合库存、记录销售和审计。

销售保存商品、规格、数量、售价、总额和当时可靠单位成本的快照。后续修改商品资料不改变历史销售结果。

## 9. 拿货

用户选择商品和规格，填写正整数数量与大于 0 的进价。系统在事务中增加规格库存、更新聚合库存、记录采购和审计，并沿用现有加权平均成本规则。

采购属于现金支出，但不能再次从经营盈利中扣除，否则会重复计算已售商品成本。

## 10. 账本与经营数据

账本汇总销售收入、采购现金支出、其他收入和其他支出。经营盈利口径固定为：

```text
经营盈利 = 可靠成本销售毛利 + 其他收入 - 其他支出
```

缺少可靠成本的销售仍计入收入，但不得伪造毛利，也不得计入经营盈利。前端不得用占位、估算或演示数值补造经营结果。

## 11. 停用与安全删除

- 停用商品不参与普通卖货、拿货、库存调整和普通 AI 匹配，但历史记录保留，可重新启用。
- 永久删除只面向误建且无历史商品，由 owner 在 Web 商品编辑的危险区域发起并二次确认。
- 资格要求：后台聚合库存为 0、小程序全部规格库存为 0、无销售、采购、库存操作、业务审计及处理中 AI 入库引用。
- 任一条件不满足时禁止永久删除并引导停用。
- 永久删除不删除历史业务数据；`code` 不重排、不复用。

## 12. AI 商品识别

AI 从商品图片中提取名称、品牌、类别、规格和明确可见的真实货号等受控特征。Node 服务随后只在当前门店真实商品库中匹配，返回唯一匹配、最多三个候选或无匹配。

页面展示的商品、真实货号、售价、库存和历史采购信息来自数据库，不使用模型生成的经营字段。低置信度、重复货号、多候选或只命中停用商品时不得自动确认。

## 13. AI 拍照入库与人工确认

1. 用户拍摄或选择采购单图片。
2. AI 只提取受控的多行商品信息。
3. 服务端匹配当前门店商品和规格，生成内存草稿。
4. 用户逐行确认商品、规格、数量和进价。
5. 全部行有效后再次确认。
6. Node 在同一事务中更新库存、采购记录、后台聚合库存和审计。

AI 不自动创建商品或规格，不生成内部 ID/`code`，不直接写数据库。无匹配、规格不唯一、数量或进价异常、停用商品命中都必须人工处理后才能提交。批量事务支持幂等重试，任一行失败时整体回滚。

## 14. 系统职责与数据同步

| 组件 | 职责 |
| --- | --- |
| 微信小程序 | 高频经营交互、规格选择、本地状态和同步提示 |
| Vue Web | 低频管理、核对、经营分析与权限界面 |
| Node.js | 微信/Demo 会话、`store/state`、商品目录、卖货/拿货事务、AI 流程 |
| Go | Web 会话、商品管理、聚合库存、分析、员工权限、安全删除和审计 |
| MySQL | 店铺成员、门店状态、后台业务表、会话和审计 |

Node 与 Go 共享同一 MySQL 和 `storeId`，但使用独立会话。当前小程序规格库存保存在 `store_states`，Web 商品表保存聚合库存；这是封版兼容边界，不在 v1.0.1 重构为统一 SKU 或统一交易表。

## 15. 安全与部署

- 正式公网仅通过 Nginx HTTPS 提供服务；Node、Go、MySQL 只监听回环地址。
- Web：`https://shanshanwink.online/pingping/`
- Node：`https://shanshanwink.online/pingping-api/v1`
- Go：`https://shanshanwink.online/pingping-admin-api/v1`
- AppSecret、数据库密码、JWT Secret、DashScope Key、私钥和生产环境文件只保存在服务器受限位置，不进入仓库。
- 小程序与 Web 的账号、会话和权限边界独立；每次请求都校验当前账号状态、角色和门店。
