## Executive Summary

- **建议拆成“手机端现场操作 + 网页后台集中管理 + 共用服务端”三层。** 手机端保留查货、卖货、单笔拿货、现场拍照和提醒等高频即时动作；后台承接批量维护、删除、盘点、经营分析、权限和导入导出。
- **第一批最应该迁出的功能是商品深度编辑与删除、批量盘点/库存修正、完整盈利分析、收支记录管理、基础资料设置和数据导出。** 这些功能在手机上信息密度高、误操作代价大，而且往往需要键盘、表格和多条件筛选。
- **不能只搬页面，必须先改数据架构。** 当前数据按微信 OpenID 保存为一个完整 `state`，手机修改后整包覆盖云端，且用户角色固定为店主。直接增加网页后台会造成并发覆盖，也无法实现可靠的员工权限、操作审计和多门店。
- **建议先做后台 MVP，不立即追求大型 ERP。** 第一阶段解决商品批量管理、供应商/分类设置、库存修正与记录、员工权限和 Excel 导入导出；采购审批、多门店和专业财务继续后置。

## 1. 本次拆分要解决什么问题

当前小程序同时承担了现场记账、商品资料维护、库存治理、经营分析和系统设置。随着商品、规格、员工和历史记录增加，会出现以下问题：

1. 商品规格、价格、供应商和库存同时编辑时，手机表单过长，批量操作效率低。
2. 删除商品、删除补录收支、直接修改库存等高风险动作离日常操作过近。
3. 7 天、30 天、12 个月趋势、商品排行、每日明细和收款构成不适合在窄屏中长期分析。
4. 复制 CSV 到剪贴板只是临时导出方式，无法满足规范的导入、导出、对账和留档。
5. 当前只有店主角色，无法区分店员、财务和管理员能看什么、能改什么。

拆分目标不是让手机端“功能越少越好”，而是让每个终端只承担最适合它的任务。

## 2. 拆分判断标准

| 判断问题 | 更适合手机端 | 更适合管理后台 |
| --- | --- | --- |
| 是否必须在货架、收银台或进货现场立即完成 | 是 | 否 |
| 是否以单条、少字段、几秒完成为主 | 是 | 否 |
| 是否需要批量选择、表格、复制粘贴或键盘输入 | 否 | 是 |
| 是否需要跨月、多条件筛选和对比分析 | 只看摘要 | 是 |
| 误操作是否可能造成大范围数据损失 | 仅允许低风险动作 | 是，并增加权限和审计 |
| 是否属于员工日常高频工作 | 是 | 管理人员低频使用 |
| 是否属于基础资料、规则或权限配置 | 通常不适合 | 是 |

## 3. 现有功能拆分结论

### 3.1 保留在手机端的核心功能

| 现有功能 | 处理结论 | 手机端保留范围 | 原因 |
| --- | --- | --- | --- |
| 微信登录 | 保留并改造 | 微信快捷登录、切换店铺、查看当前身份 | 微信身份在小程序内体验最好 |
| 首页经营概览 | 保留 | 今日销售、今日盈利、库存、缺货/临期提醒、最近变动 | 店主需要随时快速查看 |
| 商品搜索与库存查询 | 保留 | 按名称、编号、货号、分类搜索；查看规格库存 | 货架现场高频使用 |
| 快速新建商品 | 保留精简版 | 名称、分类、一个默认规格、拍照，可稍后完善 | 新货到店时需要先占档 |
| 商品拍照 | 保留 | 相机/相册上传商品图片 | 手机采集最方便 |
| 单笔拿货/增加库存 | 保留 | 选择商品规格、数量、进价和可选供应商 | 属于到货现场动作 |
| 单笔卖货 | 保留 | 商品、规格、数量、售价、收款方式、备注 | 收银现场必须快速完成 |
| 快速库存核对 | 保留但收紧 | 单个规格填写实际库存，必须填写原因 | 现场发现差异时需要即时修正 |
| 低库存、缺货和临期提醒 | 保留 | 提醒列表、查看商品、快速处理 | 适合移动提醒与巡店 |
| 最近记录 | 保留精简版 | 最近拿货、卖货、库存变化，按日查看 | 方便现场快速核对 |
| 今日账本 | 保留摘要 | 今日/昨日/本月的收入、成本、盈利和少量最近明细 | 手机适合看结果，不适合深度分析 |
| 账号和同步状态 | 保留 | 当前账号、店铺、同步状态、退出登录 | 与当前使用环境直接相关 |

### 3.2 迁到管理后台的功能

| 功能 | 后台需要提供的能力 | 手机端如何处理 | 迁出原因 | 优先级 |
| --- | --- | --- | --- | --- |
| 商品完整档案维护 | 批量新建/编辑；颜色尺码矩阵；价格、货号、位置、图片、阈值维护 | 只保留快速创建和基本查看 | 字段多、规格组合复杂，适合大屏和键盘 | P0 |
| 商品删除/停用 | 停用优先；删除需二次确认、权限校验和影响提示 | 移除直接删除按钮，仅允许“申请停用”或不提供入口 | 高风险且会影响编号、库存和历史引用 | P0 |
| 分类、品牌、供应商管理 | 新增、重命名、合并、停用、排序、默认值 | 表单中只选择已配置项，必要时允许临时新增待审核项 | 属于全店基础资料，不应散落在商品表单 | P0 |
| 批量库存盘点 | 盘点单、按分类/货位录入、差异汇总、确认生效 | 保留单规格快速核对 | 批量盘点需要长表格和集中确认 | P0 |
| 库存修正与异常处理 | 修正原因、审批、撤销/冲正、操作审计 | 普通店员只提交差异；店主可做有限单条修正 | 防止直接改库存破坏可追溯性 | P0 |
| 完整出入库记录 | 日期、操作人、商品、类型、原因等多条件筛选与导出 | 只显示近期和简单筛选 | 历史记录量大，手机列表难核对 | P0 |
| Excel 导入导出 | 商品模板、库存模板、错误行提示、标准 `.xlsx/.csv` 导出 | 移除“复制库存表格数据”或仅保留分享最近报表 | 批量数据天然适合桌面文件操作 | P0 |
| 员工与权限 | 邀请成员、角色、页面权限、数据范围、禁用账号 | 只展示当前角色和允许的入口 | 权限配置低频、高风险、需要总览 | P0 |
| 完整盈利分析 | 自定义日期、趋势、每日明细、商品排行、收款构成、对比 | 只保留今日/本月摘要 | 图表与多维分析更适合宽屏 | P1 |
| 补录收支管理 | 完整列表、筛选、编辑、删除/冲正、附件和操作人 | 可保留“快速记一笔”，普通店员可不展示 | 删除和修改财务记录需权限与审计 | P1 |
| 销售记录纠错 | 销售作废、退货/退款、冲正、原因记录 | 手机只新增销售，必要时提交纠错申请 | 不能靠直接改历史数据解决差错 | P1 |
| 采购与供应商分析 | 采购记录、供应商汇总、采购成本趋势、对账 | 手机只登记单笔到货 | 适合集中核对与长期分析 | P1 |
| 系统设置 | 低库存阈值、分类规则、收款方式、编号规则、业务开关 | 手机只读取生效后的配置 | 规则修改会影响全店，应集中管理 | P1 |
| 审计日志与数据恢复 | 谁在何时改了什么、变更前后、撤销/恢复策略 | 不在手机端提供完整日志 | 属于安全和事故处理能力 | P1 |

### 3.3 两端都要有，但展示深度不同的功能

| 共享能力 | 手机端 | 管理后台 |
| --- | --- | --- |
| 商品查看 | 快速搜索、库存和售价信息 | 完整档案、批量筛选与修改 |
| 库存状态 | 当前库存、缺货、临期提醒 | 全量库存、货位、盘点和差异分析 |
| 拿货/销售记录 | 新增和查看近期记录 | 全量查询、导出、纠错和汇总 |
| 盈利 | 今日/本月摘要 | 自定义周期、多维分析、导出 |
| 账号 | 当前角色与店铺 | 成员、角色、权限和账号停用 |
| 消息提醒 | 接收并处理提醒 | 配置阈值、范围和接收人 |

两端必须使用同一套服务端数据和权限规则，不能各自维护一份再互相同步。

## 4. 建议的目标产品结构

### 4.1 手机端：现场经营助手

建议继续保留当前五个底部入口，但收紧各入口职责：

1. **首页**：今日概览、待关注事项、最近变动。
2. **商品**：搜索、库存查看、快速建档、查看商品。
3. **记一笔**：拿货/加库存、卖货、快速收支、单规格库存核对。
4. **账本**：今日/昨日/本月摘要和近期记录，不承载完整经营分析。
5. **我的**：当前店铺、角色、同步状态、退出和后台入口说明。

手机端应遵循“新增优先、查询其次、管理最少”的原则。删除、批量修改、规则配置和历史数据改写不应出现在日常操作路径中。

### 4.2 网页后台：集中管理工作台

建议后台采用以下一级导航：

| 后台模块 | 首期页面 |
| --- | --- |
| 经营看板 | 今日/本月概览、异常提醒、待处理事项 |
| 商品中心 | 商品列表、商品编辑、规格矩阵、批量导入、停用 |
| 库存中心 | 实时库存、盘点单、库存修正、出入库记录 |
| 采购与供应商 | 拿货记录、供应商档案、采购汇总 |
| 销售与收支 | 销售记录、退货/冲正、其他收入支出 |
| 经营分析 | 趋势、商品表现、收款构成、报表导出 |
| 员工与权限 | 成员、角色、数据权限、账号状态 |
| 基础设置 | 分类、品牌、阈值、收款方式、编号和提醒规则 |
| 操作日志 | 关键变更、变更前后值、操作人和时间 |

| 记拿货/卖货 | ✓ | ✓ | ✓ | 可选 |

| 完整商品编辑 | ✓ | ✓ | — | — |
| 商品停用/删除 | ✓ | 按授权 | — | — |

| 查看成本和盈利 | ✓ | 按授权 | — | ✓ |
| 补录/冲正收支 | ✓ | 按授权 | — | ✓ |

权限必须由云函数/API 在服务端校验，不能只靠前端隐藏按钮。

## 7. 建后台前必须完成的数据与技术改造

### 7.1 当前架构的主要限制

1. 云端以 `store_<OpenID>` 或 `store_<AppID>_<OpenID>` 为文档 ID，本质上是“账号即店铺”，不支持一个店铺多个成员。
2. 云函数只提供整包 `pull` 和 `push`，修改任意一条数据都会覆盖完整店铺状态。
3. PRD 已明确多人同时修改采用最后写入覆盖；网页后台加入后，并发覆盖概率会明显上升。
4. 用户角色在客户端固定为 `owner`，没有服务端成员关系和权限模型。
5. 商品图片目前可能保存为本机临时/持久路径，跨设备和后台不一定可访问，应迁到云存储并保存文件 ID/HTTPS 地址。
6. 商品删除后重新连续编号会改变现有商品编号。后台、导出和多人协作上线后，编号应作为稳定引用，建议改成“编号永不复用、停用不重排”。

### 7.2 推荐的数据结构

至少拆成以下集合或等价的服务端实体：

- `stores`：店铺资料和状态。
- `store_members`：店铺、用户、角色和状态。
- `products`、`product_specs`：商品与规格。
- `inventory_balances`：当前库存。
- `inventory_operations`：不可随意改写的库存流水。
- `purchases`、`sales`：采购与销售业务记录。
- `finance_entries`：额外收入/支出及冲正关系。
- `suppliers`、`brands`、`categories`：基础资料。
- `settings`：店铺级规则。
- `audit_logs`：关键操作审计。

### 7.3 推荐的服务端规则

1. 每次写入只修改对应实体，不再推送整个 `state`。
2. 售出、拿货、盘点确认等同时影响多张表的操作必须使用事务。
3. 库存不允许直接覆盖；正常变化写流水，错误通过冲正或有原因的修正单处理。
4. 所有写接口校验店铺成员身份、角色、数据范围和记录版本。
5. 使用版本号或更新时间做并发控制，发现旧数据提交时提示刷新，不静默覆盖。
6. 重要操作记录操作者、来源终端、变更前后值和时间。

## 8. 分阶段实施建议

### 阶段 0：共享底座，先于后台页面

- 建立 `storeId` 与店铺成员关系，不再用 OpenID 直接代表店铺。
- 拆分整包状态，提供商品、库存、销售、采购和收支的细粒度 API。
- 建立服务端权限、事务、并发控制、审计日志和云端图片。
- 编写旧 `store_states` 数据迁移与回滚方案。

**完成标志：** 手机和网页同时修改不同记录时不会互相覆盖；无权限用户即使绕过页面也无法调用写接口。

### 阶段 1：后台 MVP

- 商品列表、完整编辑、批量导入和停用。
- 分类、品牌、供应商和低库存规则。
- 实时库存、盘点单、库存修正和全量流水。
- 员工邀请与基础角色权限。
- 标准 Excel/CSV 导入导出。

**完成标志：** 店主可以在后台完成首次建账、批量维护和月底盘点，日常店员仍可只用手机完成销售和到货登记。

### 阶段 2：经营与风控

- 完整盈利分析、商品排行、收款构成和自定义报表。
- 销售退货/冲正、收支纠错和审批。
- 操作日志查询、异常提醒和数据恢复工具。

### 阶段 3：多店经营

- 多门店、跨店查看和调拨。
- 分店数据权限、区域汇总和门店对比。

## 9. 暂不建议纳入首期后台的能力

- 完整财务会计、税务申报和净利润核算。
- 复杂采购审批、供应商结算和应付账款。
- 顾客会员、积分、优惠券和线上商城。
- 多仓库、多门店调拨。
- 小票、标签和扫码枪硬件集成。

这些能力会显著扩大业务边界，应在商品、库存、权限和审计底座稳定后再评估。

## 10. 验收标准

### 10.1 终端职责

- 店员可以在手机端 1 分钟内完成卖货或到货登记。
- 店主可以在后台批量维护商品和规格，不需要逐条操作手机表单。
- 手机端不提供普通店员可直接触发的商品删除、历史财务删除和批量库存覆盖。
- 手机账本默认只展示经营摘要，完整分析在后台可用。

### 10.2 数据一致性与安全

- 手机与后台操作写入同一店铺数据源，库存结果一致。
- 并发修改不会静默覆盖，冲突会被拒绝或要求刷新。
- 卖货、拿货和盘点确认具备原子性，不出现记录成功但库存未变的状态。
- 每条高风险变更都能查到操作者、时间、原因和变更前后值。
- 退出或禁用员工后，服务端立即拒绝其继续写入。

### 10.3 迁移与兼容

- 旧 `store_states` 数据可完整迁移商品、规格、库存、拿货、销售、收支和操作记录。
- 迁移前后总库存、销售收入和有成本记录的商品毛利核对一致。
- 迁移失败可回滚，旧数据在验收完成前保持只读备份。

## 11. 评审时需要确认的问题

1. 店员是否允许查看成本价和盈利？建议默认不允许。
2. 商品“删除”是否可以统一改为“停用”？建议上线后台后以停用为主，只允许店主清理从未发生业务的误建商品。
3. 手机端是否继续允许店主完整编辑商品？建议默认仅保留受限编辑，复杂规格和批量资料统一走后台。
4. 其他收入/支出是否允许店员录入？建议可按角色开关，并由财务或店主在后台审核/冲正。
5. 首期后台是单店专用还是从一开始支持多店？建议数据模型预留 `storeId`，界面先只做单店。

## 12. 依据与假设

- 本说明书依据当前 `app.json` 注册页面、各页面交互、`utils/store.js`、`utils/auth.js`、`utils/cloud-sync.js`、`cloudfunctions/store-sync/index.js` 和现有 PRD 编写。
